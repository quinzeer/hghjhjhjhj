# Infrastructure du plan d'exécution — orchestrateur, GPU, stockage, déploiement, UI, rendu, CI

> Consulté le : 2026-09-28 · Auteur : researcher · Version : 1 · Portée : options d'architecture du plan d'exécution pour trancher l'ADR-001 — orchestrateur durable léger, ordonnancement GPU (4× RTX 4070 Ti Super), stockage d'artefacts adressé par contenu, déploiement Docker Compose + NVIDIA Container Toolkit, interface de validation mobile, Remotion/Blender/ffmpeg, CI GitHub Actions.

## Synthèse

- Aucun orchestrateur généraliste étudié n'est « léger » au sens opérationnel pour une équipe de 1 humain + Claude : la plupart exigent un service serveur séparé (Temporal, Hatchet, Dagster, Prefect, Inngest self-hosted, Restate) avec ses propres cycles de mise à jour. Seuls **DBOS Transact (Python)**, **Procrastinate** et **PgQueuer** s'intègrent comme bibliothèques directement sur Postgres, sans service à héberger en plus [S1][S23][S25].
- **Recommandation** : DBOS Transact Python (MIT, Postgres, exécution durable en bibliothèque) comme socle de reprise/idempotence, complété par une fine couche maison en Postgres pour l'affinité GPU, la préemption des brouillons et les plafonds de coût — ces trois besoins sont propres au studio et ne sont fournis nativement par aucun outil du marché [S1][S2].
- **MinIO est à exclure** : l'édition open-source (AGPLv3) est officiellement en fin de vie depuis 2025, gelée, dépôt GitHub archivé le 25/04/2026 ; seule l'offre commerciale AIStor continue, avec un palier gratuit limité à un seul nœud [S30][S31][S32]. Pour un stockage mono-machine, **disque local + index Postgres adressé par hash** suffit ; **SeaweedFS** (Apache-2.0, très actif, v4.47 le 14/09/2026) est le meilleur plan B S3 si un vrai stockage objet devient nécessaire [S35][S36].
- **Windows + WSL2 est incompatible avec l'architecture « un worker par GPU »** : Docker sous WSL2 ne peut filtrer un GPU précis par index, seul `--gpus all` fonctionne, confirmé par la documentation officielle NVIDIA [S39]. Ceci tranche l'hypothèse du §0 de la mission en faveur d'Ubuntu 24.04 natif, qui supporte nativement `device_ids` via NVIDIA Container Toolkit [S37][S38].
- Docker Compose sait réserver des GPU précis par service (`deploy.resources.reservations.devices.device_ids`), ce qui permet de faire tourner une instance ComfyUI dédiée par carte (flags `--listen`, `--port`, `--cuda-device`), pilotée par API `/prompt` et websocket de statut [S38][S40][S41].
- **Remotion** reste gratuit pour un individu ou une entreprise ≤ 3 salariés en 2026 (Claude n'étant pas un salarié) ; au-delà, licence payante obligatoire [S44]. **n8n** (Sustainable Use License) et **Tailscale** (plan Personal gratuit) sont utilisables gratuitement pour un usage interne, avec une zone grise Tailscale si le studio est identifié comme une entité commerciale via un domaine professionnel [S42][S43].
- GitHub Actions est gratuit et illimité en minutes sur runners standard pour un dépôt public, mais sans GPU (le GPU n'existe que sur les « larger runners » payants) — la CI reste donc 100 % mocks/fixtures, conforme à la contrainte machine sans GPU du §4 [S45][S48].
- Aucun chiffre de performance Remotion (images/s, temps de rendu) n'a été trouvé dans la documentation officielle consultée ; un benchmark interne (`make bench-models`-like) reste nécessaire en phase 3.

### Pile recommandée pour l'ADR-001 (synthèse de l'agent, appuyée sur les constats ci-dessus)

1. **Orchestrateur** : DBOS Transact Python (constat 1) comme socle de reprise/idempotence/cron, + une fine couche maison en Postgres (tables `gpu_workers`, `task_priority`, `cost_ledger`) pour l'affinité GPU précise, la préemption des brouillons et les plafonds de coût — aucun outil étudié ne fournit ces trois besoins nativement (constats 1-11). *Plan B* : Procrastinate (constat 8), plus minimal, si les abstractions DBOS gênent. *Plan C* : exécuteur 100 % maison sur `SKIP LOCKED` façon PgQueuer (constat 9, 11) si un contrôle total est requis. *Coût d'un retour arrière* : faible dans les trois cas — ce sont des bibliothèques Python sur un schéma Postgres qui reste notre propriété ; changer d'outil ne migre aucune donnée hors de notre contrôle, seulement du code de retry/checkpoint (jours, pas semaines).
2. **File/planification** : Postgres lui-même (via la queue intégrée de DBOS/Procrastinate/PgQueuer), sans broker séparé — conforme à §6.8. *Plan B* : ajouter Redis uniquement si un besoin de pub/sub temps réel apparaît (ex. notifications websocket à grande fréquence), non justifié par le volume actuel (constat 10).
3. **Ordonnancement GPU** : 4 services Docker Compose, un par carte, épinglés via `device_ids` (constat 12), chacun lançant sa propre instance ComfyUI headless avec `--cuda-device`/`--port` dédiés, pilotée par API `/prompt` + websocket (constat 15) ; gestion du chaud/froid des modèles en VRAM et préemption des brouillons confiées à la couche maison au-dessus (aucun outil du marché ne le fait nativement — constat 11).
4. **Stockage d'artefacts** : disque local du serveur GPU, arborescence par hash SHA-256 des entrées, index Postgres (`artifacts(hash, path, size, step, created_at, refcount)`) pour la déduplication et la rétention — pas de couche S3 nécessaire pour une seule machine (constat 20). *Plan B* : SeaweedFS (constat 19) si un accès multi-machines (Mac, mini-PC) ou une réplication devient nécessaire. *Plan C* : Garage (constat 18), à valider hors GitHub avant adoption. **MinIO exclu** (constat 17). *Coût d'un retour arrière* : faible — le nom de fichier (hash) ne change pas, seule la couche d'accès (chemin local vs appel S3) est remplacée, avec une colonne `backend` ajoutée à l'index.
5. **Déploiement** : Docker Compose + NVIDIA Container Toolkit sur **Ubuntu 24.04 natif** (constat 13), jamais Windows+WSL2 pour la machine GPU (constat 14) ; mise à jour par `git pull && docker compose up -d --build`.
6. **Interface de validation** : FastAPI + HTMX (constat 23), exposée sur le réseau domestique via Tailscale plan Personal (constat 21). *Plan B* si le studio devient une entité commerciale visible (domaine pro) : WireGuard auto-hébergé (aucune ambiguïté d'usage) ou palier payant Tailscale « Starter ». *Coût d'un retour arrière* : faible, changement de couche réseau uniquement.
7. **Notifications/déclencheurs** : n8n sur le mini-PC Beelink (constat 22), conforme Sustainable Use License pour un usage interne.
8. **Rendu** : Remotion (constat 24-25) pour le motion design/texte, Blender headless + OptiX pour le procédural 3D (constat 26), ffmpeg + NVENC en conteneur `nvidia/cuda` pour l'encodage (constat 27, 16).
9. **CI** : GitHub Actions gratuit (dépôt public), 100 % mocks/fixtures, aucun test réellement GPU en CI (constats 28-31) ; `make gpu-smoke` reste le seul juge de vérité GPU, exécuté sur la machine réelle.

## Questions ouvertes

- DBOS Transact Python : la documentation consultée ne confirme pas explicitement un mécanisme de routage vers un worker précis (par ex. « exécuter cette étape sur le worker GPU n°2 ») ni de mécanisme d'annulation/préemption natif — à vérifier directement dans la documentation avancée (`docs.dbos.dev`) avant de bâtir la couche maison dessus.
- Le contenu détaillé de `docs.blender.org` (arguments CLI `-b`, `--cycles-device`, `OPTIX`) n'a pas pu être extrait par l'outil de récupération pendant cette session (page rendue dynamiquement) ; à confirmer par `blender --help` directement sur la machine GPU en phase 3.
- Aucune version/date de release précise n'a pu être confirmée pour Garage (le miroir GitHub ne publie pas de releases) ; à vérifier sur `git.deuxfleurs.fr` ou via `cargo`/leur documentation de téléchargement avant toute adoption.
- Aucun chiffre de performance officiel pour Remotion (images/s ou secondes de rendu par seconde de vidéo) n'a été trouvé ; nécessite un benchmark interne sur la machine cible (4× RTX 4070 Ti Super).
- Le comportement exact de Prefect 3 et Dagster sur le choix de base de données par défaut (SQLite vs Postgres en production) n'a pas pu être confirmé dans les pages consultées pendant cette session ; à revérifier si l'un de ces outils est retenu en plan B.
- Le statut juridique exact d'un studio « 1 humain + Claude » vis-à-vis de la clause « not intended for commercial use » du plan Tailscale Personal n'est pas tranché par la documentation (dépend du statut fiscal/juridique du studio, hors périmètre de cette recherche technique) ; à trancher avec un avis humain si le studio se structure en entité commerciale.
